Terminal-Bench 2 · 控制变量实验

Agent 的问题，还是模型的问题？

Pi 换成 GPT-5.6-Sol 后，模型调用减少 75%，仍然通过。Hermes 也明显变快，却在最终像素正确性上失败。结论不是二选一：模型决定了大部分效率差距，Agent 与模型的配合决定能否稳定收尾。

2026 年 9 月 21 日同一任务、镜像与资源每组一个样本
实验条件结果判断失败原因录制证据

实验条件

任务固定为 make-mips-interpreter：实现 JavaScript MIPS 解释器，运行 Doom 并输出正确画面。五组实验使用相同任务树、固定镜像、1 CPU、2 GiB 内存和 1,800 秒上限；Harbor 自动重试为 0。

新增两组均使用 GPT-5.6-Sol、Responses API 和 high reasoning：Hermes 0.19.0 与 Pi 0.86.1。Hermes 最初的 Chat Completions 请求被服务端拒绝，修正为 Responses API 后重新启动独立 trial；失败记录保留，不计入下表。

判断：模型影响效率，组合影响正确率

模型影响很大

Pi 从 DeepSeek 换到 5.6 Sol 后仍然通过：调用从 75 降到 19，输入减少约 81%，输出减少约 89%，用时减少约 83%。此前 Pi 的高消耗不能归因于 Pi Agent 本身。

不是单纯的模型排名

Hermes 换到同一模型后，调用、Token 和时间同样大幅下降，但 reward 从 1 变成 0。Hermes＋DeepSeek 能通过，说明不能简单判定“Hermes 不行”；这是 Agent、提示、工具与模型共同形成的结果。

这轮最重要的修正：Pi＋5.6 Sol 比原 Codex＋5.6 Sol 样本还少 8 次调用、约 47 万输入 Token。旧实验中“Codex 明显更省”的现象，主要来自模型与协议没有控制一致。

Hermes 为什么失败

不是 API、录制器或 Harbor 误判。Hermes 正常完成 Agent 执行并生成 BMP，验证器三项检查通过两项：

  • VM 能运行：通过。
  • /tmp/frame.bmp 存在：通过。
  • 图像与参考帧相似度：0.8065，低于要求的 0.95。

Hermes 检查了 BMP 尺寸、格式与运行日志，还调用视觉分析判断“画面正常”，但没有发现像素结果错误。它完成了功能闭环，却没有完成验证闭环。

录制证据

  • Pi＋5.6 Sol：reward 1；19/19 调用完成独立传输核对，录制状态 verified。
  • Hermes＋5.6 Sol：reward 0；Agent 原生会话与代理事件可分析，但 pcap 有 4 个 capture drops，独立传输核对未通过，不能宣称完整捕获。
  • 任务判分与录制完整性分开：Hermes 的像素失败来自 Harbor verifier，不依赖 pcap 是否完整。

边界

每个组合只有一个样本。这足以说明旧差距不能全部归因于 Agent，但不足以给 Agent 或模型做稳定性排名。下一步应固定协议和参数，每组重复 3–5 次，比较通过率与分位数。
