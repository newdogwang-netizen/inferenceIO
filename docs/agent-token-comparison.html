Terminal-Bench 2 本机实验复盘

同一个终端任务，27、61、75 次模型调用

Codex、Hermes 与 Pi 都跑了同一道 MIPS 解释器任务。三个通过样本中，后两组累计输入 Token 分别达到 Codex 的 3.40 倍和 3.83 倍。录制让我们看见：差距从哪里开始，又有哪些数字需要放在一起读。

让 JavaScript 运行一个 MIPS 程序

任务是 make-mips-interpreter。环境提供一个 MIPS ELF 可执行文件及相关源码，Agent 要实现 vm.js，处理指令执行、内存和系统调用，让程序启动 Doom 并把渲染帧保存下来。验证器检查实际产物。它同时考验读代码、理解二进制格式、实现和调试，适合观察较长的工具调用链。任务来源

本批实验使用 Harbor 0.22.0，在相同任务内容和相同固定镜像上分别启动 Agent。任务资源配置为 1 CPU、2 GiB 内存、10 GiB 存储；Agent 与验证器的时间上限均为 1,800 秒。每次 trial 的 Harbor 自动重试为 0，另行启动的修复实验单独保留记录。

三个通过样本分别是 Codex 0.154.0＋GPT-5.6-Sol、Hermes 0.19.0＋DeepSeek-V4-Pro-0813、Pi 0.86.1＋同一个 DeepSeek 服务端模型。DeepSeek 使用 Fireworks 托管接口，模型标识为 accounts/fireworks/models/deepseek-v4-pro-0813；官方权重页标注 MIT 许可。本文测量的是这些具体的 Agent、模型与服务组合。服务端模型 / 官方权重与许可

  1. 冻结输入。登记任务树、镜像 digest、Agent 版本和运行参数；Harbor 为每个 trial 启动独立任务环境。
  2. 包住实际 Agent 进程。Harbor 调用本地审计适配器，适配器把固定运行时放进容器，通过 iorec 启动 Agent。录制中常见的 /opt/iorec-agent/ 就是容器内运行时与包装器路径。
  3. 保留两条观测链。代理侧记录请求、响应与流事件；任务网络命名空间的 pcap 和 TLS key log 独立核对任务进程到 recorder proxy 这一跳，不覆盖 proxy 到 Provider 的上游连接。原始证据加密保存。
  4. 分别出结论。Harbor 验证器判任务，iorec 检查完整性和传输一致性，Platform 展示模型调用、工具请求及结果证据。一次通过不会替代另一项检查。

这是本机审计 profile，使用专门的 namespace、非 root 运行和受限出口配置，未作为官方排行榜成绩提交。Codex 使用 high reasoning；Hermes 的 max_turns 为 60；Pi 设置 thinking off，并关闭扩展、skills 与 context files。这些条件不同，结果不能单独归因于模型或 Agent 框架。方法见审计运行手册。

这三次 Harbor 验证器 reward 都是 1。下面的“模型调用”是录制中的模型接口请求数；“工具结果 / 请求”是平台能重建并按工具 ID 关联的证据。一次工具调用可以批量执行多条 shell 命令，返回结果也可能是错误，不能直接当作等粒度的成功工作步数。

差距在第一次写实现前就形成了

相同任务固定的是目标、初始环境和验收条件。Agent 自己决定读哪些文件、何时开始实现、做多少验证，因此不会产生固定步数。把调用链按工具行为展开，一个容易复核的里程碑是首次写入目标文件 /app/vm.js。在此之前的源码阅读和小程序测试也可能是有效工作。

大输出会跟着历史进入后续请求

Pi 第 7 次调用读取 my_stdlib.c，工具返回 51,245 个字符。平台在后续模型输入里观察到同一工具 ID、同一内容哈希 68 次。Hermes＋DeepSeek 的一条 14,101 字符读取结果也出现 53 次。这记录的是同一结果被重新携带，不代表文件被重新读取几十遍。

Codex 此次使用 Responses WebSocket，第 2-27 次调用通过 previous_response_id 延续上下文；另外两组使用 Chat Completions SSE。增量传输让工具文本不必每次重新出现在网络请求里，但服务端上下文和用量仍应看 usage。线上文本重复次数不能直接换算成三组的模型计算量。

本次证据支持的解释是：较长的前期探索增加了请求数量，较大的历史内容又随着后续调用累计进入输入统计。模型能力、Agent 提示与工具策略、缓存和服务速度各自贡献了多少，还需要控制变量实验。

几百万输入 Token 是怎样累加的

dashboard 的输入总数是每次有上报的 input_tokens / prompt_tokens 之和。历史上下文会在多个请求里计入，因此累计值不等于原始任务长度或单次上下文窗口。Pi 的单次最大输入只有 171,939，累计输入却达到 6,465,285。

75 次有 usage 的 Pi 调用，平均输入约 86,204 Token；Codex 是 62,600；Hermes 已观测的 56 次是 102,653。Pi 的输入差距可以直接拆成 2.78 倍请求数量 × 1.38 倍平均输入 ≈ 3.83 倍。Hermes 只能对已有 usage 的请求做同类计算，不能把 56/61 当成完整覆盖。

按各自调用序号将轨迹分为前、中、后三段，Pi 每次平均输入从约 2.97 万升到 7.56 万、15.33 万；Codex 为 2.42 万、7.49 万、8.87 万。两者都在累积上下文，Pi 的较长尾段让总和继续增加。

计算后，Pi 虽然累计输入是 Codex 的 3.83 倍，估算费用却更低。原因是模型单价不同，而且 Pi 的缓存输入占比达到 97.34%。所以 Token 规模适合解释轨迹负担，不能直接当作美元费用排名。

Codex 的计费桶来自 Agent 原生 trajectory：26 次生成调用共有 1,682,756 个 prompt tokens；其中 1,588,427 个为 cached input、94,251 个为 cache write、78 个为普通 input。平台表里的 1,690,213 还包含一次 generate=false 请求的 7,457 个输入 Token，Agent 原生费用汇总未纳入这次请求。所有金额都是根据用量与价格快照重算的估算，不是 Provider 账单。

能读出 Token，不代表每个字节都录全了

Token 覆盖回答“多少次调用上报了用量”；独立传输核对回答“线上消息与代理证据是否一致”。Pi 的 75/75 usage 与不完整 pcap 可以同时成立。

matched attempt 的粒度不能跨协议当作模型调用比较：Codex 一个 WebSocket 连接承载了 27 次模型接口请求，而 HTTP/SSE 样本通常按请求形成 attempt。当前表格使用平台核对快照，历史离线报告可能保留不同版本的 gap 分类。

Hermes 56/61 的五个缺口

第 16、31、35 次调用均为 HTTP 200，但响应录制分别缺少 3、1、9 个正文 chunk，规范化无法可靠给出 usage；第 54 次是图像输入不受支持的 HTTP 400；第 61 次在关闭前没有观察到响应。HTTP 200、完整正文、usage 可用是三个不同条件。缺失部分保留为未知。

后续请求保留的历史工具信息显示，第 16、31、35 次对应的都是调查操作，不影响首次写入发生在第 36 次的判断。这种交叉核对能补充部分工具轨迹，却无法补回缺失的响应字节与 usage。

更正此前长任务文章：旧 Hermes manifest 的 3,573 是汇总 capture drops，其中 pcap packets_dropped 为 3,560，另有 13 个响应正文 chunk 缺口。把 3,573 全称为“pcap 丢包”不准确。本次按事件拆分；旧证据保留，后续修复不能自动把它升级为完整录制。

这批实验给出的判断

在这个固定任务和这组配置下，Codex＋GPT-5.6-Sol 的一次成功运行使用了更少的模型请求、可重建工具交互、上报 Token 和墙钟时间。Hermes 与 Pi 搭配 DeepSeek 也通过了任务，前置调查更长，历史内容在更多调用中累加，形成了更大的累计输入；缓存显著改变了理解费用的方式。

这仍然是一个任务、每个组合一个通过样本。Agent、模型、思考配置、API 协议、工具粒度、缓存状态及录制器版本同时存在差异，两份 DeepSeek 组合的独立传输核对也未通过。因此不能据此给模型家族或 Agent 框架排出普遍优劣，也不能把约 8 倍墙钟时间全解释为服务端推理慢。

下一轮可在本次 Hermes / Pi 同模型对比的基础上，进一步统一配置并重复多次，再在同一个 Agent 内比较模型；报告通过率、调用次数、缓存与非缓存输入、输出和用时分位数。大工具输出截断与摘要策略可以单独作为变量。补齐录制缺口后，再观察这些改动是否同时降低 Token 并保持正确率。

本文仅复盘现存证据，没有新增付费模型试验。
