iorec · 采集端工作原理

iorec 如何录下 Agent 的一次工作

一个面向不同 Agent 的统一录制工具与平台：把模型通信、工具执行和任务结果放在一起，让每一步都有据可查。

2026 年 9 月 22 日约 7 分钟基于当前实现
解决什么代理原理工具执行如何核对真实例子覆盖边界

不只看最终回答，还要看执行过程

Agent 说“已完成”，不代表脚本成功运行；终端里有日志，也不代表所有模型请求都被记录。排查问题时，我们需要知道：发给模型什么、返回了什么、调用了哪个工具，以及工具实际怎么结束。

iorec 的目标是统一录制，不是给 Agent 排名。本机采集端保留证据，平台把证据整理成可查询的模型调用、工具执行和任务进度。不同 Agent 的日志可以进入同一个视图，但各自的覆盖范围仍单独标明。

采集端做四件事

1. 包住一次 Agent 启动

用 iorec run … -- <agent 命令> 启动任务。启用模型代理时，采集端先建立录制 ID、存储目录和本地监听端口，再把连接配置注入它启动的 Agent 子进程，记录进程生命周期和退出状态。它不默认监控整台机器，也不会把配置写进用户的全局 shell 环境。

2. 在模型通信链路上留一份记录

这里不是泛指“抓包”，而是两种明确的接入方式：修改 API 地址的反向代理，以及隔离实验中的透明 TLS 拦截。

方式 A：修改 base URL，让 Agent 主动连本地代理

以 OpenAI 兼容接口为例，Agent 原本请求 https://api.openai.com/v1/responses。iorec 启动一个本地 HTTP 服务，并向子进程注入类似下面的配置：

OPENAI_BASE_URL=http://127.0.0.1:43123/v1
IOREC_PROXY_URL=http://127.0.0.1:43123

43123 只是示例；默认监听 127.0.0.1:0，由操作系统分配空闲端口。Agent 随后把同一个 API 请求发到本地 /v1/responses；iorec 根据 --upstream，再向真正的服务发起请求。

对 Agent，iorec 是 HTTP 服务端；对模型服务，iorec 是 HTTP 客户端。这就是反向代理的角色，而不是模型本身。实现上使用 Rust 的 Axum 接收请求、reqwest 发起上游请求，保留请求方法、正文和必要鉴权头，按新连接重建 Host 等传输字段。概念可参见 HTTP 规范中的反向代理定义。

# 接入示意：先准备 iorec 密钥及 Agent 自己的鉴权配置
iorec run --key-file ./iorec.key \
  --upstream https://api.openai.com \
  --provider openai \
  -- your-agent-command

这里不是设置系统级 HTTP_PROXY。前提是 Agent/SDK 读取该 base URL，或有专门适配器注入 provider 配置；只包住启动命令，不能保证所有请求都经过代理。不同 Agent 的适配可能改变协议选项，例如当前 Codex 显式代理适配会关闭 WebSocket，不能假定与原始运行完全相同。

HTTPS 怎么处理？这个普通模式下，Agent 到本机回环地址是 HTTP，iorec 到真实服务是 HTTPS；iorec 作为 TLS 客户端正常解密收到的响应，因此能看到正文。它没有破解 Agent 与原服务之间的 TLS，而是建立了两段独立连接。本地明文入口不能直接暴露到公网。

方式 B：不改 API 地址，用隔离网络和临时 CA 接入

受控 Linux 实验可显式启用 --task-netns --transparent-proxy。Agent 仍访问原来的 HTTPS 域名，采集端在它的专属 network namespace（网络命名空间）里配置 nftables DNAT：只把预先确认的模型 IPv4 地址和端口重定向到录制器入口。

HTTPS 还需要第二步：为本次运行生成临时 CA 和目标域名证书，通过 SSL_CERT_FILE、NODE_EXTRA_CA_CERTS 等把信任配置传给支持这些设置的子进程。Agent 的 TLS 在录制器终止；录制器再建立一条到真实服务、正常验证上游证书的 TLS 连接。这是授权实验里的 TLS 中间人代理，不是被动旁路抓包，也不是关闭证书校验。

这种方式不保证任意 Agent 都兼容。证书固定（certificate pinning）、不读取信任配置的客户端、自定义 DNS，或任务依赖被隔离策略阻断的其他网络地址，都可能失败。它只用于明确启用的隔离任务，不改整台机器的信任库。

流式输出怎么既转发，又录制？

HTTP/SSE 路径不等整段回答结束再返回。每收到一个正文数据块，代理把它交给两个异步路径：一份进入有界采集队列，记录序号、长度、哈希和按策略保留的字节；另一份继续转发给接收方。请求体和响应体都按这种方式流式处理。

SSE 解析器再跨数据块累积字节，按空行分隔还原 event / data 事件；网络数据块、SSE 事件、模型 Token 不是一一对应的。WebSocket 则在两端连接之间双向转发消息，另记消息方向、顺序和关闭状态，不把它当 SSE 解析。SSE 的事件边界见标准定义。

HTTP/SSE 采集队列满时会等待容量，形成背压，因此不能承诺“零延迟、零影响”；WebSocket 采集另有消息与字节预算。写盘失败、预算溢出或流不完整都需要留下缺口，不能把“仍在转发”当成“已经录全”。

流式响应会先留下事件和正文，再由平台重组为响应文本、工具调用和服务端返回的 Token 用量。规范化视图是原始证据的解释，不是另一份模型回答。

3. 把工具请求与实际执行接起来

模型协议
记录模型请求了什么工具、传了哪些参数。提出调用，不等于已经执行。
Agent 原生日志 / Hook
记录 Agent 报告的工具返回、错误和可用退出码。Codex、Hermes、Pi 已有相应适配。
实际工具后端
直接采集进程退出码、耗时、stdout/stderr，以及显式选定文件的前后哈希与差异。目前已验证 Pi 0.86.1 的 Linux bash 后端。

平台按明确的调用 ID、工具名和兼容会话关联这些来源，不靠“时间差不多”猜测匹配。同一次执行有多份证据，也不会因此重复算成多步。

具体到 Pi：通过扩展接口替换 bash 的底层执行 operations，保留工具参数和返回格式；Python 进程包装器启动真实命令，从独立管道读取 stdout/stderr，用 waitid / wait 取得进程状态，并采样显式选定的文件。调用 ID 和会话 ID 一起传入，方便和模型请求关联。HTTP 代理本身看不到本机脚本怎么执行，所以这层需要单独接入。

4. 先落盘，再交给平台

核心录制按事件序号写入本机，正文以 blob 单独保存并关联 SHA-256；默认加密，并通过 iorec verify 检查相应完整性约束。随后可在线上传，或结束后受控导入；平台再解析、索引和展示。工具补充附件单独导入，不改写原录制。

在线上传先传正文对象，再传事件批次，以平台确认的 durable_seq 续传，重复提交按身份和哈希校验处理。普通在线上传不携带 pcap 和 TLS secrets；需要平台复核这些敏感证据时，走 operator 受控的 platform bundle 导入。离线导出包是明文，必须私有保存并在完成后清理；不能把本机加密误解成平台全程无需解密。

这样可以从任务进度下钻到模型请求，再查看关联的工具参数、输出和退出状态。对进程采集的原始输出，目前平台提供有限预览，完整保留的字节仍在本机。

怎么知道代理有没有漏录？

在受控实验中，可以另外启用 --pcap --tls-keylog：用 tcpdump 抓取任务网络包，同时从支持的 TLS 运行时或录制器 TLS 端点获得 NSS 格式的会话密钥日志。iorec transport-audit 再调用 TShark 解密、重组 HTTP/1.1、HTTP/2 或 WebSocket 应用数据，与代理记录核对。只有 pcap、没有对应 TLS 会话密钥，不能据此读出 HTTPS 正文。

这提供了一条独立于代理正文写入路径的核对来源，不是拿同一份 Agent 日志证明自己完整；但它仍依赖本机抓包和密钥采集，不是对本机操作者的远程防篡改证明。

当前这类核对针对受控的 Agent → 录制器 链路，不涵盖录制器 → 模型服务的完整端到端过程。它不是默认开启；出现丢包、解码缺口或不完整响应时，会保留失败状态。

任务成功、工具执行成功、录制完整，是三个不同的结论。脚本退出码为 0 不代表任务答对；页面有响应正文，也不代表完整性核对通过。

一个已经录到的真实例子

在一次本地 Pi 实验中，模型生成 CSV 汇总脚本与测试，再通过 bash 执行，得到独立检查通过的汇总结果。平台记录了 4 次模型调用、3 次 bash 执行。

3 个模型工具请求、3 条 Agent 工具结果、3 条进程观测，最终关联成 3 条工具执行记录，不是 9 步。每条能查看模型来源、命令、stdout/stderr、退出码和选定文件变化。

这是实际模型与进程的本地录制验证，不是模拟日志，也不是 Harbor benchmark。该次未做 pcap/TLS 独立核对，不能据此宣称所有流量或系统活动都已捕获。

统一入口，不等于全量覆盖

  • 接入决定覆盖：原生日志适配不等于实际进程观测；Pi 的 bash 接入也不代表 read、write、MCP 或其他 Agent 的工具后端已覆盖。
  • 缺失不能当作成功：没有退出码、输出截断、关联不上，都应明确显示，不能补成 0 或完整。
  • 敏感数据有边界：核心模型录制默认加密；新增工具输出、报告和 diff 目前仍是本机权限受限的明文补充文件，尚未纳入原始加密链，也没有新增自动脱敏器。不要公开原始录制。

iorec 想做到的，是让“Agent 做了什么”可以追溯到证据，同时让“哪里没有录到”也清楚可见。
