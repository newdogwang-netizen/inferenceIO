# 12 · 与采集端路线图的对齐

> **实现状态（2026-09-16）**：P0～P4 与采集端 M0～M7 的发布范围已落地。
> 操作者已批准以 18,000 秒替代草案中的 24 小时稳态门槛；最终门槛仍要求

## 1. 已决：平台与采集端并行开发

2026-09-15 决定：平台作为并行轨道开发，不再后置到 v1.1 之后。采集端路线图已同步更新（§2 设计约束、§3.2 平台轨道、§4.14、§5、§7 v0.3 gate）。约束：

- **"采集端独立可用"原则不变**，上传与控制客户端可关闭，关闭后等同 v1.0 Local Recorder。
- **契约先于实现**：v0.1 事件 envelope 加批次层发布为共享 schema 文件（路线图 UP-000），采集端与平台 CI 双向校验。M0 结束前 envelope 不冻结，平台只做 schema 与 fake collector。
- **同步点**：P0 ← M0 envelope 冻结；P2 resolve ← M1 显式 ID 事件；P3 coverage 重算 ← M3 指标事件；P4 与 M7 同时发布。

## 4. 已决配置与明确后置项

1. **实现语言。** 平台 API 与 Worker 使用 Go；采集端使用 Rust，并通过受约束的子进程协议接入 AgentSight/eCapture。
2. **Recording 切段策略。** 大小与时间先到先切，采集端默认 64 MiB 或 900 秒；`stream_key` 以 CaptureRun 为作用域，平台可跨连续 Recording 重建。
3. **文件导入。** 首版已实现，导出端与导入端共同执行 5 GiB 硬上限、路径/类型/数量/摘要校验和无覆盖发布。
4. **敏感项目策略。** 正文采集、字段脱敏、路径白名单、分级 TTL 与远端删除均由本地上限约束；部署方仍须根据 PHI/合规要求配置项目策略，平台配置不能放宽本地策略。
5. **ClickHouse。** 明确后置到 PostgreSQL 锁竞争或查询延迟达到扩容阈值之后，不是首版发布依赖。
6. **模型评审。** 明确不进入本次发布范围且默认关闭；provider、预算与数据出域审批确定前不得启用。
