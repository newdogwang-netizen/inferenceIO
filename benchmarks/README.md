# Performance evidence

Performance JSON reports in this directory are generated by `tools/perf_harness.py` against a release binary. They include the binary hash, platform, workload, methodology, raw aggregate measurements, and integrity validation for every recorded run. Other qualification and tooling reports state their own evidence sources and narrower scope.

`2026-09-18-m3-admission-ledger-linux-x86_64.json` records 159 passing Python regressions, including 16 shared-ledger tests and an existing real encrypted-export fixture. Synthetic cases exercise all 14 declared reservations, launch linkage, inherited locks, conservative unknown-cost handling and stale-report recovery fences. An actual incomplete-plan preflight was rejected without a job, launch intent or ledger. This is not a real-provider matrix, billing verification, paired-performance result or five-hour acceptance.

The benchmark alternates direct-first and recorded-first rounds. Both paths use the same Python standard-library HTTP/SSE client and the built-in loopback fake server. The recorded path enables full body capture and at-rest encryption. The harness never connects to a non-loopback address.

These reports are environment-specific observations, not universal performance guarantees. CI executes a small correctness smoke without enforcing noisy latency thresholds. The operator-approved release gate is a separately identified 5-hour (18,000-second) final-candidate soak report, superseding the draft roadmap's 24-hour duration.

Example:

```bash
python3 tools/perf_harness.py benchmark \
  --iorec target/release/iorec \
  --output benchmarks/local.json \
  --requests 400 --warmup 20 --rounds 5 --concurrency 4

python3 tools/perf_harness.py soak \
  --iorec target/release/iorec \
  --output benchmarks/soak-5h.json \
  --duration-seconds 18000 --rate 1 --concurrency 4

python3 tools/connected_soak.py \
  --iorec target/release/iorec --api http://127.0.0.1:48090 \
  --project-token-file /private/project.token \
  --admin-token-file /private/admin.token \
  --output benchmarks/connected-soak-5h.json --work-dir /tmp/iorec-cs \
  --duration-seconds 18000 --collectors 20 \
  --compose-project iorec-connected \
  --compose-file iorec-platform/deploy/compose.yaml \
  --compose-file iorec-platform/deploy/compose.qualify.yaml

PYTHONPATH=tools python3 tools/platform_release_provenance.py \
  --platform-root iorec-platform --iorec target/release/iorec \
  --connected-report benchmarks/connected-soak-5h.json \
  --output benchmarks/platform-release-provenance.json \
  --compose-project iorec-connected \
  --compose-file iorec-platform/deploy/compose.yaml \
  --compose-file iorec-platform/deploy/compose.qualify.yaml

PYTHONPATH=tools python3 tools/real_agent_qualification.py \
  --iorec target/release/iorec \
  --work-dir /private/iorec-agent-qualification \
  --output benchmarks/2026-09-16-real-agent-cli-transport-linux-x86_64.json \
  --gemini-executable /private/gemini-0.60.0/bin/gemini \
  --codex-executable /private/codex-0.154.0/bin/codex \
  --claude-executable /private/claude-2.1.273 \
  --hermes-executable /private/hermes-0.19.0/bin/hermes \
  --replace-existing
```

The connected harness expects the named Compose project to be running already; start that project with both `iorec-platform/deploy/compose.yaml` and the loopback-only `iorec-platform/deploy/compose.qualify.yaml` override. Repeat `--compose-file` for both files so controlled API and Worker stop/start operations use the same merged definition as the running project. Keep the same required Compose environment variables exported for the harness process.

The platform provenance generator accepts only a passing, release-qualified connected report. It requires the report's image IDs and end-of-run Compose configuration/file hashes to match the still-running project, rechecks live hardening, hashes the platform source tree plus generator inputs and container binaries/tools, and publishes an atomic report only when every check passes.

The real-Agent harness launches each CLI with an explicit non-secret environment, pins the Agent executables plus Gemini's Node runtime and TShark decoder, rejects any input/source hash drift across the run, and refuses non-private or pre-existing work directories, unexpected attempt counts, incomplete transport audits, or report replacement unless `--replace-existing` is explicit. A passing replacement archives the prior report under its digest before publishing the new atomic JSON. Its provider is the shipped loopback fixture; no qualification prompt is sent to a public provider.
